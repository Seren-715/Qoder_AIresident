# LifeHack 参赛体验与实现建议

状态：讨论草案；与现有计划和 Phase 1 Spec 配合使用。2026-11-09。

## 定位

**给一只有自己生活的 AI 小鸭，留一间会等待你回来的小屋。**

小鸭会在小屋里活动、偶尔出门旅行，回来后带回一张属于它的明信片。玩家不需要持续照顾；打开网页时，可以看到自己离开期间它做了什么。

核心价值是轻负担陪伴和好奇心：它有可观察的日常，用户的互动会留下痕迹，旅行产生可回看的共同经历。小鸭个性、官方形象素材和名称仍待确认。

## 参赛体验：三分钟看到完整故事

评委第一次打开就应看到小鸭在小屋里活动，而不是先填写表格或输入 API Key。建议流程：

1. 打开网页，看到小鸭正在活动；引导文字说明可以摸摸它、和它说话或观察它。
2. 输入名字、选择一种性格（可提供默认值和跳过按钮）；轻触互动，看见动作或气泡反馈。
3. 点击「演示一天」，时间加速并展示两三次活动变化；加速只用于演示，不冒充真实经过的时间。
4. 点击「邀请出门」，小鸭收拾行李并离开；演示模式在短时间内完成一次旅行。正常模式仍可让小鸭按自己的状态决定出门，避免把自主生活变成纯按钮驱动。
5. 小鸭归来，玩家打开有地点、见闻和一句关联用户经历的话的明信片；再次进入能在相册中看到它。

演示按钮应标明模拟，且不能覆盖真实存档：建议复制当前状态进入临时演示，退出后恢复；若实现成本过高，单独提供预设演示档，并明确其独立性。

## 产品优先级

| 优先级 | 建议 | 验收 |
| --- | --- | --- |
| P0 | 小屋 + 小鸭自主活动 | 不操作时也能观察到活动和状态变化；手机屏幕可用 |
| P0 | 本地存档与离线补算 | 重开页面能恢复，并展示离开期间的真实模拟记录 |
| P0 | 一次完整旅行及明信片 | 旅行开始、归来、明信片入册均可验证；演示模式可快速体验 |
| P0 | 一次有反馈的互动 | 摸头或聊天后有可见变化，结果能与后续经历关联 |
| P0 | 公开部署和降级 | Qoder Sites 公网可访问；模型不可用时小屋和旅行仍可体验，并清楚标示降级 |
| P1 | 依据经历生成日记或明信片文案 | 只引用实际发生的事件；失败时模板兜底 |
| P1 | 纪念品装饰小屋 | 一件纪念品能被看见并关联旅行记录 |
| 暂缓 | 真实地图、账号、跨设备、多人、QQ 接入、复杂自主规划 | 比赛版先验证核心体验 |

现有计划中聊天属于 P0。考虑约 30 小时预算，建议至少保留简单聊天，但若模型接入影响核心流程，优先保证互动、旅行和可靠展示，再决定聊天是否降为 P1；这是建议，尚未修改原计划。

## 怎样让「记住」可以被验证

不必一开始建设复杂记忆系统。先保存少量有来源的数据：小鸭名字和性格、用户明确选择的偏好、最近互动、旅行事件、明信片。每条事件记录时间、类型和内容；生成文字时仅提供少量相关事件。

示例：用户选择「喜欢雨天」→ 某次旅行遇到雨景 → 明信片提及「想起你说喜欢雨天」。如果没有这条记录，就不应编造用户偏好。聊天和明信片可以在适当位置提示引用的经历，方便验证；允许用户清除存档。

旅行先由程序生成目的地、事件和纪念品，再让模型根据事实润色；校验失败、超时或超预算时使用模板。避免把生成文本作为状态变化的唯一依据。

## 实现建议

- 按现有 Spec 将时间推进、活动选择和状态更新放在独立模拟模块；界面读取状态，减少耦合。
- 存档带版本号；限制离线补算时长、事件数量和单次计算量，并覆盖损坏存档与刷新恢复场景。
- 模型调用经服务端函数，密钥存放平台 Secret；公开访问前确认费用上限、请求限流和异常处理。具体平台能力以实际配置验证为准。
- 区分「体验生成」与「模板体验」，模型失败时明确显示，不把模板文案描述为实时生成。
- 测试优先覆盖：旅行状态转换、刷新后恢复、离线补算、演示档不污染正式档、模型超时降级；另用手机和无痕窗口验证公开链接。
